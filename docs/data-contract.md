# Формат данных и отдельный преобразователь XLSX

Статус: действующий контракт схемы версии 1 и реализованного преобразователя M4. Обновлено 6 октября 2026 года. Основной план — [plan.md](plan.md). Рабочий JSON содержит реальную историю; [тестовые JSON и описание](../data/fixtures/README.md) сохранены отдельно для проверок кода.

## Подготовка данных

Данные считаем корректными и полными по умолчанию. Отдельный локальный скрипт читает XLSX, преобразует записи в JSON и сохраняет файл для сайта. На сайте нет формы загрузки, импорта, редактора или проверки данных; приложение только читает готовый JSON.

Не нужны валидаторы схемы, ID, ссылок, дублей, имён, годов или мест, отчёты валидации, словари разрешения конфликтов, статусы и подтверждение полноты состава. Обычные ошибки чтения XLSX или записи файла можно показать стандартным сообщением скрипта. Тесты преобразования проверяют код на корректных примерах.

Исходные XLSX — локальные входные файлы, исключённые из Git и его истории. Клон содержит готовый JSON, список источников и преобразователь; для повторного преобразования XLSX необходимо получить отдельно. Загрузка, тесты и сборка приложения не требуют исходных XLSX.

## Исходная таблица

Изучен предоставленный `tournament-with-players-12826.xlsx`: один лист `Worksheet`, заголовок в строке 1, 574 строки игроков и 90 команд. Каждая строка — игрок; место, ID и название команды повторяются для его состава. В примере составы от 6 до 9 игроков, есть дробные места и одинаковые фамилия/имя у разных ID.

| Колонка XLSX | Результат преобразования |
| --- | --- |
| `Место` | `participations[].place`, число без округления |
| `Team ID` | `teams[].id` и `participations[].teamId`, строка |
| `Название` | `participations[].displayName`, историческое название |
| `IDplayer` | `players[].id` и элемент `participations[].playerIds`, строка |
| `Фамилия`, `Имя` | `players[].name`, «Фамилия И.» |
| `Отчество` | Игнорируется |
| `Город`, `Флаг` | Игнорируются |

Колонки читать по заголовкам. Полностью пустые строки пропускать. Удалять крайние пробелы в строковых значениях; числовые ID превращать в обычные строки (`49804` → `"49804"`), текстовые ID сохранять, включая ведущие нули. Это преобразование формата, а не проверка допустимости ID.

В `players[].name` сохранять целиком фамилию из колонки `Фамилия` и первый Unicode code point имени, приведённый к верхнему регистру, с точкой: «Фамилия И.». Составные фамилии сохраняются целиком. Крайние пробелы удаляются при чтении ячеек. Отчество не используется и не сохраняется в дополнительных полях. Пустое имя даёт только фамилию, пустая фамилия — только инициал имени с точкой, оба пустых поля — пустую строку. Совпадение сокращённых подписей не объединяет ID; UI добавляет исходный ID к совпадающим подписям. Справочное имя по-прежнему берётся из последнего проведения.

Сохранять всех игроков без фильтра по флагу и без ограничения шестью. Место `6.5` сохранять как `6.5`; UI может показывать `6,5`. Не выводить диапазоны мест из дробного значения.

Все новые исходники называются `tournament-with-players-<tournamentId>-<year>.xlsx`, например `tournament-with-players-1710-2011.xlsx`. При разборе имени файла (без пути) скрипт извлекает `tournamentId` как строку (`"1710"`) и `year` как число (`2011`). Правило разбора: `^tournament-with-players-(\d+)-(\d{4})\.xlsx$`; ведущие нули ID сохраняются. ID относится к отдельному проведению в источнике, а не ко всей ежегодной серии. Год для сортировки и JSON берётся только из имени файла и не дублируется в `data/tournaments/chr/sources.json`.

Название проведения пользователь указывает в `data/tournaments/chr/sources.json`, поскольку его нет в таблице или имени файла. Внешний `tournamentId` служит идентификатором исходной выгрузки; схема JSON сайта остаётся прежней: ID проведения — строка года, ID участия — `<year>:<teamId>`. По запросу UI от 2 октября 2026 года ID источника сохраняется в необязательном строковом поле `editions[].tournamentId`, чтобы год был ссылкой на соответствующий турнир рейтинга.

Ранее изученный образец `tournament-with-players-12826.xlsx` уже переименован в `tournament-with-players-12826-2026.xlsx` с фактическим годом 2026 и включён в реальный набор. Для других исходников год также берётся из имени файла; угадывать его или использовать условный год из fixtures нельзя.

## Формат JSON сайта

Корневой объект: `schemaVersion: 1`, `editions`, `teams`, `players`, `participations`. Версия описывает формат; загрузчик не выполняет отдельную проверку версии или данных.

| Сущность | Поля |
| --- | --- |
| Проведение | `id: string`, `year: number`, `name: string`, `tournamentId?: string` |
| Команда | `id: string`, `name: string` |
| Игрок | `id: string`, `name: string` |
| Участие команды | `id: string`, `editionId: string`, `teamId: string`, `displayName: string`, `place: number`, `playerIds: string[]` |

В каждой серии одно проведение на год. Каждый турнир хранит отдельный корневой объект версии 1; ID и вычисленные истории между JSON не объединяются. ID проведения — строка года, ID участия — `<year>:<teamId>`. Название относится к конкретному проведению и сохраняется в JSON. По согласованному упрощению UI отдельная строка названия проведения удалена: карточка показывает историческое название команды, год, место и состав. При скрытом годе выбор сохраняется, карточка закрывается; для просмотра состава нужно вернуть год в диапазон.

URL и дата проведения не входят в JSON и параметры скрипта. Ссылка года формируется из `tournamentId`: `https://rating.chgk.info/tournaments/<tournamentId>`. Скрипт сохраняет этот ID из имени XLSX, включая ведущие нули. Старые демонстрационные наборы без поля остаются совместимыми со схемой версии 1: год показывается обычным текстом. Хронология определяется `year`. Проведения, участия и полные вычисленные цепочки идут от старых лет к новым; справочники сортируются по строковым ID. Текстовых списков истории в UI нет. Колонки диаграммы отображаются по убыванию года: самый новый слева; это не меняет вычисленные цепочки. Имена не используются как ключи: разные ID с одинаковым именем остаются разными игроками. Если отображаемое имя одного ID меняется между годами, справочное имя берётся из последнего проведения; дополнительное согласование не нужно. Так же обновляется справочное название команды, а её историческое название остаётся в каждом участии.

Составы считаются полными. Поля статуса полноты нет. Связи, позиции SVG и выделение вычисляются из JSON и не сохраняются в нём. Годы без данных не дополняются.

## Вход скрипта и обновление

Пример записи `data/tournaments/chr/sources.json`; название условно:

```json
{
  "editions": [
    {
      "file": "source/tournament-with-players-1710-2011.xlsx",
      "sheet": "Worksheet",
      "name": "Пример ежегодного турнира — 2011"
    }
  ]
}
```

Пути XLSX разрешаются относительно каталога `data/tournaments/chr/sources.json`. Если `sheet` не указан, читать первый лист. Список содержит файл и название каждого проведения; ID источника и год извлекаются из имени XLSX.

Преобразование выполняется только при явном запуске команды по необходимости; запуск приложения, обычная сборка и открытие сайта используют уже готовый JSON и не пересоздают его. Каждый запуск преобразователя требует всех XLSX из списка, включая неизменённые годы: результат строится целиком, а существующий JSON не используется как вход.

Скрипт выполняет следующие действия:

1. Читает список файлов, извлекает ID турнира и год из имени каждого XLSX по указанному шаблону и обрабатывает проведения по возрастанию года, независимо от порядка списка.
2. Читает строки выбранного листа и группирует их по `Team ID`, даже если они не расположены подряд.
3. Сохраняет проведение с названием, годом и `tournamentId` из имени XLSX. Создаёт одно участие команды с местом и названием из первой строки группы и всеми ID игроков.
4. Создаёт общие справочники по ID; имена игроков и справочные названия команд обновляет при обработке следующего года.
5. Сортирует проведения по году, справочники по строковым ID, участия по году/месту/строковому `teamId`, ID игроков в составе — лексикографически.
6. Сохраняет единый JSON в `public/data/chr/history.json` одной строкой без форматирующих отступов, с завершающим переносом. Компактное форматирование не меняет схему, значения и порядок массивов.

Для нового года добавить XLSX с именем `tournament-with-players-<tournamentId>-<year>.xlsx` в `data/tournaments/chr/source/` и запись с файлом и названием в список, затем запустить `npm run convert:xlsx`. Для исправления года заменить его исходный файл или метаданные и снова запустить команду. Результат каждый раз пересоздаётся целиком, а не дописывается в старый JSON. Для выбранной серии — `npm run convert:xlsx -- <slug>`: только её исходники и JSON; без аргументов используется `defaultTournament` из `data/tournaments.json`. Каждый турнир имеет свои `sources` (относительно корня проекта) и `history` (относительно `public/`). Для другого списка и выходного пути: `npm run convert:xlsx -- /путь/sources.json /путь/history.json`. Чтение XLSX выполняет ExcelJS, зависимость разработки для Node; она не входит в браузерную сборку. После преобразования выполняются проверки и `npm run build`. Публикация включена: push в main запускает GitHub Actions и публикует готовые JSON обеих серий. Команды и процедура описаны в [README](../README.md#подготовка-и-обновление-данных).

После успешного преобразования локальные XLSX можно удалить без изменения готового JSON или работы сайта. Для последующего обновления необходимо восстановить весь набор из списка; поэтому исходники рекомендуется хранить отдельно. В Git сохраняется обновлённый JSON и, при изменении метаданных или списка файлов, `data/tournaments/chr/sources.json`; XLSX остаются вне Git.

## Пунктир в диаграмме (уточнение от 2 октября 2026 года)

По решению пользователя пунктир означает, что между двумя известными участиями игрока есть хотя бы одно проведение в полном наборе `editions`, в котором он не участвовал. Разрыв календарных лет сам по себе не задаёт пунктир: соседние доступные проведения 2008 → 2010 и 2019 → 2025 соединяются сплошной линией при участии игрока в обоих. Отсутствующий во всём наборе год не означает пропуск игроком турнира. Это уточнение заменяет прежнее календарное правило; фильтр диапазона не меняет `isGap` и не создаёт связей.
