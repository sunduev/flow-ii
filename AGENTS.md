# Инструкции для агентов flow-ii

## Назначение и источники требований

Проект — статический сайт независимых историй N ежегодных турниров: результаты команд по годам, исторические составы и полные цепочки игроков. Общение и документация — на русском; идентификаторы кода — на английском.

Это базовая локальная адаптация подхода [Superpowers](https://github.com/obra/superpowers): понимание задачи → план → небольшие изменения → проверка → ревью. Она работает без установленного плагина; наличие этого файла не означает, что skills Superpowers установлены или вызваны.

Перед работой прочитай:

1. `AGENTS.md` — процесс работы.
2. `docs/plan.md` — согласованные требования, стек и порядок этапов.
3. `docs/data-contract.md` — схема JSON и правила преобразования ежегодных XLSX, затем соответствующий файл `milestones/M*.md` — границы текущего задания и критерии приёмки.
4. Затронутый код, README, проверки и отчёты предыдущих этапов, если они уже есть.

`docs/references/tournament-history.html` — необязательный ориентир, а не утверждённый целевой дизайн. Улучшения оформления и удобства допустимы при сохранении требований продукта. `docs/draft.md` — исторический черновик; актуальная версия — `docs/plan.md`. При противоречии между актуальными требованиями зафиксируй его и уточни решение, если оно меняет продукт. Текущие указания пользователя имеют приоритет.

Не начинай реализацию M1 только из-за чтения этих инструкций. Выполняй запрошенное задание; работа над документацией не запускает разработку сайта.

Текущий независимый репозиторий — `sunduev/flow-ii`, код перенесён без прежней Git-истории. Публикация настроена по поручению пользователя 6 октября 2026 года: репозиторий публичный (`private=false`), Pages включён (`has_pages=true`, `build_type=workflow`), HTTPS включён. Workflow `Publish GitHub Pages` запускается при push в main либо вручную. Страницы — `https://sunduev.github.io/flow-ii/chr/` и `/flow-ii/studchr/`, корень перенаправляет на ЧР. Результаты — в `docs/reports/2026-10-06-flow-ii-publication.md`. Старый `sunduev/flow-chr` не изменять; исторические отчёты M6 сохранены. Коммиты и push по-прежнему выполняются в пределах поручения; push в main публикует сайт. M1–M6 завершены; расширение на N независимых серий реализовано. Реестр — `data/tournaments.json`, исходный `index.html` и код общие; после сборки готовый HTML копируется по каталогам турниров. JS выбирает серию по пути и запрашивает только её JSON; связи и навигация между сериями отсутствуют.

## Понимание и планирование

- Перед изменениями проверь файлы проекта и, если Git доступен, `git status`. Сохраняй чужие незавершённые изменения.
- Для нового или неоднозначного поведения выясни цель, ограничения и критерии результата. Обсуди варианты и зафиксируй выбранное решение до реализации, если оно меняет согласованную архитектуру или сценарий.
- Уже согласованные решения из `docs/plan.md` и текущего майлстоуна не требуют повторного проектирования или подтверждения. Рутинные детали выбирай самостоятельно в пределах задания.
- Для многошаговой реализации разбей текущий майлстоун на небольшие проверяемые задачи: конкретные файлы, изменение поведения, способ проверки и ожидаемый результат. Уточняй пути после осмотра проекта; не выдавай предполагаемую структуру за существующую.
- Сохраняй такой план в `docs/plans/M<N>-<topic>.md`; для задачи вне майлстоунов — `docs/plans/YYYY-MM-DD-<topic>.md`. Обновляй выполненные пункты и обоснованные отклонения. Небольшой правке документации достаточно краткого плана в сообщении.
- M1–M6 — этапы, а не готовые планы каждого изменения. Выполняй их последовательно с учётом зависимостей. M4 требует XLSX и метаданных каждого проведения; формат образца уже закреплён в контракте. M5 требует реального исторического набора; M6 — целевого репозитория и доступа. Отсутствующие входные данные указывай явно.

## Реализация небольшими шагами

- Выполняй одну задачу плана за раз: реализуй, проверь результат, пересмотри изменения, затем переходи к следующей.
- Для новой вычислительной логики, преобразования таблиц и исправления поведенческих ошибок используй TDD: напиши тест ожидаемого поведения, запусти и убедись, что он падает по нужной причине; внеси минимальное исправление; добейся прохождения; затем рефакторь при зелёных тестах. Тесты проверяют работу кода на корректных примерах, а не валидируют предоставленные данные.
- Проверяй контракт и наблюдаемое поведение, а не копию реализации. Используй примеры с известным ожидаемым результатом. Для ошибки добавляй регрессионный тест, когда она воспроизводится автоматически.
- Документация, конфигурация, каркас и чисто визуальные изменения не требуют искусственных unit-тестов. Проверяй их подходящим способом: чтение, проверка типов, сборка, запуск приложения и визуальная проверка. Интерактивное поведение проверяй отдельно от внешнего вида.
- Сохраняй простой стек первой версии: Vite, TypeScript, SVG, `d3-scale`, `d3-shape`, CSS, статический JSON. Добавляй зависимости по конкретной необходимости; не вводи сервер, базу данных или функции вне текущих требований.
- Разделяй модель и вычисления, отдельный скрипт подготовки JSON, диаграмму и панель состава. Скрипт не входит в браузерное приложение; сайт только читает готовый JSON. Не восстанавливай факты истории из SVG или положения узлов.

## Поиск причин ошибок

Сначала воспроизведи проблему и сохрани наблюдение: входные данные, действие, ожидаемый и фактический результат. Проследи путь данных до причины, сформулируй одну гипотезу и проверь её минимальным экспериментом. Исправляй причину и повторяй исходный сценарий и затронутые проверки. При неудаче пересмотри гипотезу, не накапливай случайные правки и не отключай проверку ради зелёного результата.

## Правила, которые должны сохраняться

- ID — строки; совпадение имён не объединяет игроков. JSON содержит версию схемы.
- Соблюдай `docs/data-contract.md`: ID проведения и год извлекаются отдельным скриптом из имени `tournament-with-players-<tournamentId>-<year>.xlsx`, название проведения задаётся в `data/tournaments/<slug>/sources.json`; одно проведение на год внутри каждой серии. Город и флаг игнорируются; в JSON сохраняется только «Фамилия И.» из отдельных колонок имени и фамилии, отчество игнорируется, игроки по флагу не отбрасываются.
- Исходные данные по умолчанию корректны и полны: ID и ссылки согласованы, игрок участвует в одной команде одного проведения. Не добавляй проверки дублей, конфликтов, мест или схемы ни в скрипт, ни в приложение; не создавай отчёты валидации и процедуры подтверждения данных.
- Название и состав относятся к конкретному участию. Переименование и возвращение игрока сохраняют историю.
- История содержит только известные участия этого турнира. Годы без данных не заполняются. Пунктир означает пропуск игроком промежуточного проведения из полного набора; календарный разрыв сам по себе не создаёт пунктир.
- Колонки диаграммы идут от новых лет к старым, самый новый слева. Вычисленные полные цепочки сохраняют порядок от старых лет к новым; текстовые списки истории в интерфейсе удалены по согласованному решению.
- Диапазон лет меняет только диаграмму: полные вычисленные истории, текущий выбор и фильтр игрока сохраняются; новые связи не создаются. Карточка состава закрывается; для состава скрытого участия нужно вернуть его год в период.
- Равные и дробные места допустимы; порядок внутри равных мест стабилен по строковому ID команды. Размер состава не ограничен шестью; статусы полноты не нужны.
- Отдельный скрипт `scripts/convert-xlsx.ts` пересоздаёт JSON выбранной серии по её списку XLSX и метаданных командой `npm run convert:xlsx -- <slug>`; без аргументов используется `defaultTournament` из реестра. Для ЧР команда `npm run convert:xlsx -- chr` сохраняет результат в `public/data/chr/history.json`. Исходники других серий хранятся в `data/tournaments/<slug>/`, результаты — в `public/data/<slug>/history.json`; общие ID не объединяются. JSON ЧР содержит реальную историю; демонстрационный набор для тестов — `data/fixtures/demo-history.json`. Подготовка данных не является функцией сайта. Достаточно обычных сообщений о технической ошибке чтения или записи файла.

## Ревью и подтверждение результата

После задачи проверь соответствие требованиям, пограничные случаи, читаемость и отсутствие лишних изменений. Перед завершением майлстоуна отдельно проверь все его критерии приёмки. Замечания проверяй по коду и воспроизводимому сценарию; исправления подтверждай проверками.

Используй фактические команды из README и конфигурации проекта: `npm test`, `npm run typecheck`, `npm run build`. Для изменений кода запускай затронутые тесты, проверку TypeScript и production-сборку; для UI также проверяй сценарий в браузере, телефонный размер и клавиатуру. Произвольные команды выбираются мышью/касанием; клавиатурный доступ проверяй для управления, ссылок годов, кнопок состава и игроков. Проверки качества начинаются с первых изменений; M5 объединил их на реальном наборе данных, M6 повторяет актуальный сценарий на опубликованном сайте.

Сообщай об успехе только после выполнения проверок и чтения их результатов. Если проверка недоступна или не выполнена, укажи это и причину. Не подменяй приёмку на реальных данных демонстрационными примерами.

## Git и передача работы

Если Git ещё не инициализирован, работай с файлами и сообщи об этом; не создавай репозиторий, ветку или worktree автоматически. Если Git есть, используй существующие правила проекта; отдельный worktree нужен для запрошенной изоляции или при мешающих чужих изменениях. Не сбрасывай чужие правки. Коммиты, push, merge и публикацию выполняй в пределах поручения пользователя.

### Авторизация и публикация GitHub Pages

На рабочем Mac доступ к `sunduev/flow-ii` сохранён в записи Связки ключей macOS с именем сервиса `chr-flow-github`. Это токен GitHub, а не SSH-ключ. При поручении на push или публикацию используй эту запись; отсутствие авторизации в `gh auth status` само по себе не означает, что доступа нет. Не проси повторно выполнить `gh auth login`, пока не проверена сохранённая запись.

Передай токен через `GH_TOKEN` только внутри отдельного процесса shell; не выводи его, не включай трассировку `set -x`, не сохраняй в файлы или конфигурацию Git:

```sh
export GH_TOKEN="$(security find-generic-password -s chr-flow-github -w)"
test -n "$GH_TOKEN" || exit 1
git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push origin main
gh run list --repo sunduev/flow-ii --limit 5 --json databaseId,status,conclusion,headSha,url
```

Если sandbox блокирует Связку ключей, запись в `.git` или сетевой доступ, используй штатный запрос расширенных разрешений для уже порученного действия. В другом окружении или при недоступной записи сообщи о конкретной причине и запроси доступ, не раскрывая секретов.

Автоматический push-триггер main включён по поручению публикации от 6 октября; после публикующего push проверь workflow `Publish GitHub Pages` именно для отправленного SHA, дождись успешной публикации и сравни публичный JSON с локальным. Инструкция обновления и ограничения кеша — в разделе «Публикация — M6 (завершён)» [README](README.md). Использование записи не даёт самостоятельного разрешения на commit, push или публикацию вне поручения пользователя.

По умолчанию выполняй план последовательно в текущем чате. Субагентов используй при явном поручении делегирования; разделяй ответственность за файлы и проверяй интеграцию.

Отчёты текстовые; новые скриншоты не сохраняются в репозиторий. Визуальные проверки остаются обязательными.

При завершении майлстоуна сохрани `docs/reports/M<N>.md`: выполненные критерии, изменённые файлы, фактические команды и результаты проверок, оставшиеся ограничения и входные данные для следующего этапа. В итоговом сообщении кратко укажи результат и проверки. Невыполненные обязательные критерии означают, что этап ещё не завершён.
