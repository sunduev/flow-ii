# Вычисления истории — M2

Все функции экспортируются из `index.ts`, используют [модель версии 1](../model/types.ts) и не зависят от DOM, SVG, загрузчика или состояния выбора. Вход считается корректным: проверки версии, дублей, ссылок, мест и годов не выполняются.

## API

| Функция | Результат |
| --- | --- |
| `createHistoryIndex(data)` | `HistoryIndex`: проведения по возрастанию `year`; справочники `editionById`, `teamById`, `playerById`, `participationById`; списки участий `participationsByEdition`, `participationsByTeam`, `participationsByPlayer` |
| `getPlayerHistory(index, playerId)` | `PlayerHistory`: справочный игрок, полные `entries` и индивидуальные `links` |
| `getRosterHistories(index, participationId)` | Полные истории всех игроков именно этого состава, в порядке его `playerIds` |
| `buildHistoryGraph(index)` | Все `playerLinks` и объединённые `backgroundLinks` |
| `getDiagramData(index, graph, range?)` | Годы от новых к старым, `participationsByEdition` и только видимые исходные связи |

Вызовы для одного игрока/участия ожидают известный ID из индекса. Корректный пустой набор поддержан; известный игрок без участия получает пустые `entries` и `links`. UI в M3 выбирает существующее участие либо показывает пустое состояние.

Участия сортируются по году, месту и лексикографическому строковому `teamId` (например, `"10"` раньше `"2"`). Для диаграммы меняется только порядок лет. Места не округляются, состав не ограничивается. Индексы и функции не меняют исходные массивы; объекты фактов переиспользуются, потребителю следует читать их без мутаций. `readonly`/`ReadonlyMap` описывают этот контракт без замораживания данных во время выполнения.

Каждый `HistoryEntry` содержит `edition` с годом и названием проведения и исходное `participation` с ID, историческим `displayName`, местом и составом. Название команды берётся из участия, не из современного справочника. Возвращения и повторное участие в той же команде остаются отдельными записями. Имена игроков не используются как ключи.

Связь содержит `sourceId` и `targetId` участия: источник всегда старше цели. Индивидуальная связь дополнительно содержит `playerId`; фоновая — `playerIds` всех игроков с той же парой концов. У каждой связи `isGap` равен `true`, если между её концами есть проведение в полном хронологическом наборе, в котором игрок не участвовал. Позиции проведений хранит `editionPositionById`. Разрыв календарных лет без промежуточного проведения не создаёт пунктир; диапазон не меняет это правило. Фон объединяет только одинаковые пары концов; UI M3 использует `isGap` для пунктира и отдельные связи игроков для выделения. Цвет и оформление здесь не задаются.

`YearRange` — включительный диапазон `{ fromYear, toYear }`. Без него видны все годы. Проекция отбирает только существующие проведения и связи, у которых оба конца видимы; не соединяет оставшиеся точки заново и не меняет `isGap`. Пустой диапазон даёт пустую диаграмму. Индекс, граф и полные истории не сокращаются. Состояние выбранной команды/игрока хранится отдельно в UI M3 и не передаётся в функцию диапазона.

## Пример для M3

```ts
import { createHistoryIndex, getRosterHistories, buildHistoryGraph, getDiagramData } from './history/index';

const index = createHistoryIndex(data);
const graph = buildHistoryGraph(index); // один раз после загрузки
const histories = getRosterHistories(index, '2024:27177'); // полные вычисленные истории
const diagram = getDiagramData(index, graph, { fromYear: 2025, toYear: 2026 });
// histories сохраняет все участия и метаданные выбранного проведения 2024.
// Диапазон ограничивает только проекцию диаграммы; текстовой панели в текущем UI нет.
// Для выделения в SVG: diagram.playerLinks, отобранные по выбранным playerId.
```

[Конкретные ожидаемые цепочки](../../data/fixtures/README.md) и [машиночитаемые сценарии](../../data/fixtures/history-scenarios.json) проверяются в `../../tests/history.test.mjs` на готовом JSON. Команда: `npm test` из корня проекта. Дополнительные небольшие корректные примеры проверяют несортированный вход, равные места, полное совпадение имён, объединение фона и пустую историю.


## Выбор и общий режим

`selection.ts` хранит `Selection { participationId, playerId, allRosters }`; изначально `allRosters=false`. `selectParticipation` сохраняет режим и сбрасывает игрока. `setAllRosters` сохраняет фильтр, если игрок входит в новый набор, иначе снимает его.

- `getSelectionPlayerIds` возвращает состав активного участия либо уникальные ID из всех участий его команды. Общий набор отсортирован по строковому ID и не зависит от активного года, диапазона или фильтра.
- `getSelectionHistories` возвращает полные цепочки этого набора; фильтр игрока применяют renderer и компактная проекция.
- `getSelectionRelations` возвращает показанные участия с признаками `sameTeam` и `additional`. Дополнительное участие не содержит игроков активного состава. Участие обеих групп остаётся обычным, в том числе при фильтре исторического игрока.
- `isRosterParticipation` отличает карточку полного состава: активное участие либо любое участие той же команды в общем режиме.
- `getSharedRosterPlayerIds` пересекает выбранный набор с составом конкретного участия и учитывает фильтр. `getTeamInfoPlayerIds` сохраняет полный список для карточек состава, а для внешних связей возвращает пересечение.

`diagram-view.ts` уплотняет участия выбранных цепочек, используя тот же общий набор и уже ограниченные диапазоном исходные связи. Новые связи не создаются.
